Runbook 03: Aurora PostgreSQL Split-Brain

Scope

This runbook covers split-brain or conflicting writer scenarios in the Aurora Global Database between Mumbai and Hyderabad.

Objective

  • Restore a single writer topology
  • Prevent data corruption and ensure transactional integrity
  • Meet RTO under 5 minutes

Preconditions

  • Aurora Global Database replication is enabled.
  • Monitoring of Aurora cluster endpoints is active.
  • Route 53 and application connection logic support fast endpoint updates.

Immediate Actions

  1. Detect split-brain via monitoring alarms on aurora:ReplicationLag and DBClusterRole.
  2. Stop writer traffic to suspect region.
  3. Confirm which region has the latest committed state using transaction logs and cluster status.

RTO Steps

  1. If Mumbai is primary and healthy:
  2. Force Hyderbad instance to read-only.
  3. Confirm no writes are accepted in Hyderabad.
  4. Re-establish replication from Mumbai to Hyderabad.
  5. If Hyderabad becomes the valid recovery site:
  6. Promote Hyderabad replica to writer.
  7. Redirect application writer traffic to Hyderabad endpoint.
  8. Pause Mumbai Aurora writes until replication is re-established.

Validation

  • Verify only one writer endpoint is active.
  • Validate application writes succeed and no duplicate transaction IDs are created.
  • Confirm Aurora replication resumes normally.
  • Review transaction reconciliation with settlement systems.

Post-Recovery Activities

  • Document split-brain root cause.
  • Review Aurora failover settings.
  • Update runbook with any procedural lessons.
  • Notify audit and compliance teams.
