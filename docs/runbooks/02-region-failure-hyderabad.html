Runbook 02: Hyderabad Region Failure

Scope

This runbook covers failover when AWS Hyderabad (ap-south-2) becomes unavailable or impaired.

Objective

  • Maintain Mumbai as active fail-safe region
  • Keep transaction continuity and RPO under 1 minute
  • Meet regulatory resilience requirements

Preconditions

  • Mumbai environment is primary and healthy.
  • Route 53 failover records are preconfigured.
  • Aurora primary cluster in Mumbai is online.
  • DynamoDB Global Tables remain writable in Mumbai.
  • Kafka primary cluster in Mumbai is available.
  • ElastiCache Redis primary cluster in Mumbai is available.

Immediate Actions

  1. Confirm Hyderabad outage through AWS Health and monitoring alerts.
  2. Adjust Route 53 weighted routing to send all traffic to Mumbai.
  3. Validate API calls through Mumbai region endpoints.

RTO Steps

  1. Ensure Aurora Global Database is still healthy in Mumbai.
  2. Verify DynamoDB writes and reads in Mumbai.
  3. Confirm Redis primary cluster health.
  4. Check Kafka replication status and adjust MirrorMaker 2 if needed.

Validation

  • Execute payments test flows in Mumbai.
  • Confirm no lagging global table writes.
  • Check cache hits and Redis keyspace.
  • Validate Kafka consumer groups and transaction event delivery.

Post-Recovery Activities

  • Document failover details and timings.
  • Monitor for any residual replication or sync issues.
  • Prepare failback plan to restore Hyderabad after service is stable.
  • Notify compliance and operations teams.
